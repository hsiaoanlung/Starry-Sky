# nbody_check.py 驗證說明

`nbody_check.py` 讀取 `Assets/Resources/Planets.csv`，用**與 Unity 相同的方法**在 Python 中重新模擬一次，然後自動檢查結果是否合理。
用途是在改了 CSV（新增天體、改質量或軌道）或調整 `dt` 之後，不必開 Unity 就能確認物理與資料沒有問題。

與 `two_body_check.py` 的差別：

| | two_body_check.py | nbody_check.py |
| --- | --- | --- |
| 天體 | 只有太陽 + 地球 | Planets.csv 全部天體 |
| 目的 | 確認積分器寫對 | 確認整個系統（資料 + 初始條件 + 積分）正確 |
| 輸出 | 能量誤差 + 軌道圖 | 能量誤差 + 每顆天體的穩定性與週期表 |

---

## 1. 執行方式

需要 Python 3 與 numpy（`pip install numpy`）。

```
cd "D:\Unity\Starry Sky\Assets\Docs"
python nbody_check.py
```

可用參數：

| 參數 | 預設 | 說明 |
| --- | --- | --- |
| `--csv` | `../Resources/Planets.csv` | 要驗證的資料表 |
| `--dt` | 0.001 | 步長（天），應與 Unity 場景中 NBodySimulator 的 Dt 相同 |
| `--days` | 100 | 模擬總天數 |
| `--sample` | 20 | 每幾步記錄一次距離與角度 |

範例：

```
python nbody_check.py --dt 0.002 --days 365
python nbody_check.py --csv 只有內行星.csv
```

29 顆天體、dt = 0.001、100 天約需 7 秒。

---

## 2. 腳本與 Unity 程式的對應

腳本把 Unity 的流程逐步重寫一次，每一段都對應一個 C# 函式：

| 腳本段落 | 對應 Unity 程式 | 內容 |
| --- | --- | --- |
| 1. 讀 CSV | `PlanetSpec.ParseCsv()` | 讀取每列天體資料，`#` 開頭略過 |
| 2. 初始條件 | `SolarSystemBuilder.Awake()` | 近日點位置、vis-viva 速度、疊加 parent、逆行 |
| 　 | `NBodySimulator.RemoveCenterOfMassDrift()` | 總動量與質心歸零 |
| 3. 重力 | `NBodySimulator.ComputeAccelerations()` | 所有配對的萬有引力加總 |
| 　 | `NBodySimulator.TotalEnergy()` | 動能 + 位能 |
| 4. 積分 | `NBodySimulator.Step()` | Velocity Verlet：半步速度 → 整步位置 → 新加速度 → 半步速度 |

兩邊使用相同的 G、相同的單位（AU、太陽質量、天）、相同的 double 精度。
唯一的寫法差異：C# 用雙層迴圈只算 i < j 的配對，Python 用 numpy 一次算完整個 N×N 矩陣，兩者數學上相同。

## 3. 驗證項目

腳本做三項檢查，前兩項有明確的通過標準。

### 3.1 能量守恆

$$\left|\frac{E_{end} - E_0}{E_0}\right| < 10^{-8}$$

$$E = \sum_i \tfrac12 m_i v_i^2 \;-\; \sum_{i<j} \frac{G m_i m_j}{r_{ij}}$$

**為什麼有效：** 孤立系統的總能量在物理上守恆。數值模擬的能量誤差來自兩種錯誤：

- **程式錯誤**：例如力的方向寫反、漏乘質量、積分順序錯，能量通常會在幾步之內就大幅偏離。
- **dt 太大**：某顆天體一圈的步數太少，誤差會逐步累積。

Velocity Verlet 是 symplectic 積分器，正常情況下能量誤差只會小幅震盪、不會持續增長，所以只要誤差維持很小，就代表程式與步長都沒問題。

**限制：** 能量是全系統加總，太陽與木星佔了絕大部分。一顆很輕的小衛星（例如火衛一，質量只有太陽的 5×10⁻¹⁵）就算算錯，對總能量的影響也非常小。所以還需要 3.2 逐顆檢查。

### 3.2 衛星與行星是否穩定

每隔 `--sample` 步，記錄每顆天體與其 `parent` 的距離 $r$，最後取整段時間的最小值與最大值，除以半長軸 $a$：

$$0.5 < \frac{r_{min}}{a} \quad\text{且}\quad \frac{r_{max}}{a} < 1.5$$

**為什麼有效：** 穩定的橢圓軌道上，距離會在近日點 $a(1-e)$ 與遠日點 $a(1+e)$ 之間變化，所以 $r/a$ 應落在 $1-e$ ~ $1+e$ 附近（再加上其他天體造成的小幅攝動）。
若天體被甩出去或掉向母星，$r/a$ 會遠超出這個範圍，標示為「脫離!」。

±50% 是很寬鬆的門檻，只用來抓「明顯壞掉」的情況。判讀時建議直接看數字：

- 數值接近 $1 \pm e$：正常。
- 明顯比 $1 \pm e$ 寬：該天體受到很強的攝動，或 dt 對它來說偏大。

例：水星 $e = 0.2056$，所以 $r/a$ 落在 0.794 ~ 1.206 是正確的。

### 3.3 實測週期與理論週期

**實測週期**：追蹤天體相對 parent 的方位角 $\theta = \operatorname{atan2}(z, x)$，每次取樣累加角度變化（處理過 ±π 的跳動），算出總共轉了幾圈：

$$\text{圈數} = \frac{|\sum \Delta\theta|}{2\pi}, \qquad T_{實測} = \frac{\text{模擬天數}}{\text{圈數}}$$

**理論週期**：克卜勒第三定律，只考慮天體與 parent 兩者：

$$T_{理論} = 2\pi\sqrt{\frac{a^3}{G(M_{parent} + m)}}$$

兩者相比：

- 理論週期**只**驗證 CSV 的 $a$ 與質量填得對（例如與 NASA 資料的週期一致）。
- 實測週期是**模擬真的跑出來的**結果。兩者接近，代表初始速度給得對、積分器也正確運作。
- 差異不會是 0，因為真實系統中還有其他天體的攝動。例如月球受太陽強烈影響，實測短約 0.45%；土衛六、木衛四也有約 0.1% 的差異。這些是真實的物理效應，不是錯誤。
- 只在轉滿 **2 圈以上**時才計算，否則離心軌道的角速度不均勻會讓結果失準，表中顯示「—」。

**注意：** 取樣間隔必須讓天體每次轉不到半圈，否則角度會判斷錯誤。預設每 20 步 × 0.001 天 = 0.02 天取樣一次，最快的火衛一（0.32 天一圈）每次約轉 23°，足夠。若改大 `--dt`，請同時把 `--sample` 調小。

為了確認腳本真的抓得到錯誤，用月球適用、但對火衛一太大的步長測試：

```
python nbody_check.py --dt 0.05 --sample 1
```

解讀：

- 火衛一一圈只有 6 步，軌道被破壞，距離跑到 1.55 倍，週期偏差 40%。
- 土衛一 Mimas 一圈 19 步，雖然沒脫離，但距離與週期已明顯偏差，表示也需要更小的 dt。
- 能量誤差只略超門檻：如 3.1 節所述，小衛星的錯誤對總能量影響很小。**所以兩項檢查都要看。**

## 5. 這個驗證能證明什麼、不能證明什麼

**能證明：**

- `Planets.csv` 的資料能組成一個穩定的系統（沒有填錯單位或數量級）。
- 初始條件的推算方法（近日點、vis-viva、疊加 parent、逆行、動量歸零）正確。
- 在指定的 dt 下，Velocity Verlet 能準確推進所有天體。

**不能證明：**

- **Unity 的 C# 程式沒有 bug。** 腳本是另一份獨立的實作，只證明「方法」是對的。若 C# 抄錯一個符號，腳本不會知道。
- **畫面顯示正確**：`orbitScale`、`displayRadius`、TrailRenderer、相機都不在腳本範圍內。
- **Unity 的效能**：Python 用 numpy 矩陣運算，速度與 Unity 的 C# 迴圈不同。
- **長時間的穩定性**：預設只模擬 100 天。要看幾年以上，請加大 `--days`。

### 在 Unity 中對照

`NBodySimulator` 每隔 `Log Every Days`（預設 100 模擬天）會在 Console 印出：

```
[NBody] t = 100.0 d, dE/E = ..., |L| = ...
```

用相同的 dt 時，Unity 印出的 `dE/E` 應與腳本同一量級（約 $10^{-12}$ ~ $10^{-10}$）。
若 Unity 的數值明顯比腳本大很多，代表 C# 程式與腳本有差異，值得檢查。

注意：Unity 的模擬時間由真實播放時間決定。若每幀需要的步數超過 `Max Steps Per Frame`，該幀剩下的時間會被捨棄，模擬會比設定的播放速度慢（畫面右上角的「實際速度」會變紅），但每一步本身仍然正確，不影響 `dE/E`。

## 6. 修改 CSV 後的建議流程

1. 用 Excel 修改 `Planets.csv` 並存檔（保留 CSV 格式）。
2. 執行 `python nbody_check.py`，用場景中的 dt。
3. 兩項都「通過」，且新天體的 r/a 接近 $1 \pm e$、週期差異在 1% 內 → 回 Unity 按 Play。
4. 若某天體「脫離!」或差異很大：
   - 先檢查該列的單位（`a` 是 AU、`mass` 是太陽質量）與 `parent` 是否正確。
   - 再試更小的 dt（例如 `--dt 0.0005 --sample 40`）。若變小後就正常，代表 Unity 場景的 dt 也要跟著調小。

---

## 7. 已知差異

- 腳本用 Python 內建的 `csv` 模組，只支援**逗號**分隔；Unity 版也接受分號。
- 腳本要求 `retrograde` 欄為 `1` 才算逆行，與 Unity 相同；欄位不存在時視為 0。
